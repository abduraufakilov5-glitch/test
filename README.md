# Учёт долгов клиентов — production v2

Мобильное PWA для реального учёта долгов магазина. Данные хранятся в Supabase/PostgreSQL. Баланс не хранится отдельным перезаписываемым числом: он вычисляется из неизменяемой финансовой истории `DEBT`, `PAYMENT`, `ADJUSTMENT`.

## Что важно в этой версии

- `DEBT` и `PAYMENT` создаются только через серверную RPC `create_transaction`.
- Сервер сам берёт владельца из `auth.uid()` и проверяет ownership клиента.
- Оплата больше текущего долга запрещена и на UI, и в PostgreSQL.
- Одновременные операции одного пользователя сериализуются advisory lock; клиент дополнительно блокируется `FOR UPDATE`.
- Каждый финансовый запрос имеет `idempotency_key`. Повтор запроса после timeout не создаёт вторую операцию.
- Прямые INSERT/UPDATE/DELETE для `transactions` через frontend запрещены RLS.
- Клиента с финансовой историей физически удалить нельзя; погашенные клиенты остаются в архиве.
- Initial migration — одна атомарная RPC. Исходные 44 записи = **24 920 сомони**.
- JSON restore — атомарный **REPLACE**. Ошибка откатывает всё. Один `backup_id` нельзя восстановить дважды.
- Service worker кэширует только оболочку приложения и библиотеку Supabase JS, но никогда не кэширует Supabase Auth/REST/RPC/financial responses.

## 1. Создайте Supabase project

1. Откройте Supabase и создайте новый project.
2. Название можно выбрать любое, например `dolgi-magazin`.
3. Выберите ближайший доступный region.
4. Создайте сильный database password и сохраните его в менеджере паролей. Этот пароль **не вставляется** в frontend.
5. Дождитесь окончания создания проекта.

## 2. Создайте базу

1. В Supabase откройте **SQL Editor → New query**.
2. Откройте локальный файл `supabase-schema.sql`.
3. Скопируйте файл **целиком** и выполните его одной командой Run.
4. Если SQL Editor показывает ошибку, не начинайте работать с реальными данными, пока ошибка не устранена.

Схема включает таблицы `clients`, `transactions`, `migration_status`, `restore_history`, RLS, constraints, indexes и серверные RPC.

## 3. Получите Project URL и Publishable key

В Supabase откройте настройки API проекта и скопируйте:

- Project URL;
- Publishable key (в старом интерфейсе может называться `anon/public`).

В `supabase.js` замените:

```js
const SUPABASE_URL = 'https://YOUR-PROJECT-REF.supabase.co';
const SUPABASE_ANON_KEY = 'YOUR-ANON-PUBLIC-KEY';
```

Frontend может содержать Project URL и Publishable/anon key. **Никогда** не помещайте в `supabase.js`, GitHub или HTML: `service_role`, secret key, database password.

## 4. Создайте аккаунт владельца

1. Откройте **Authentication → Users**.
2. Создайте пользователя с email + password.
3. Если создаёте его вручную, подтвердите email/используйте Auto Confirm.
4. Войдите этим аккаунтом в приложение.

После создания всех нужных аккаунтов отключите публичную регистрацию новых пользователей в настройках Authentication. Приложению регистрация не нужна — только вход.

## 5. Запустите локально

Не открывайте `index.html` через `file://`. Запустите HTTP server, например:

```bash
python3 -m http.server 8080
```

Откройте `http://localhost:8080`.

## 6. Выполните initial migration

1. Войдите в приложение.
2. Откройте **Настройки → Первоначальный перенос долгов**.
3. Preview должен показать **44 записи** и **24 920 сом.**
4. Проверьте список. Похожие имена специально не объединяются.
5. Нажмите **Импортировать** один раз.
6. После успеха снова откройте migration: повторный запуск должен быть заблокирован сервером.

Импорт выполняется внутри одной PostgreSQL-транзакции: либо создаются все записи и marker, либо не создаётся ничего.

## 7. Обязательная проверка финансовой логики

На тестовом клиенте проверьте по порядку:

1. `+300` → баланс 300.
2. `+50` → баланс 350.
3. `−100` → баланс 250.
4. Попытка `−300` → сообщение **«Сумма оплаты не может быть больше текущего долга.»**, операция не создаётся.
5. Нажмите **Погасить полностью** → подставится 250 → после сохранения баланс 0.
6. Клиент появится в **Архив / Погашенные**.
7. Откройте его и добавьте `+100` → он снова станет активным должником.

## 8. Double-click, retry и два устройства

Кнопка submit блокируется на время запроса. Кроме этого, база имеет UNIQUE `(user_id, idempotency_key)`.

Если запрос `+50` дошёл до сервера, но iPhone получил timeout, кнопка **Повторить** отправляет тот же `idempotency_key`; сервер вернёт существующую операцию вместо создания дубля.

Если iPhone и Mac одновременно пытаются оплатить 80 при долге 100, сервер сериализует операции. Одна оплата может пройти, вторая будет отклонена; отрицательного долга не получится.

## 9. Архив и удаление

Баланс 0 не удаляет клиента. Он показывается в архиве, а вся история остаётся.

Физическое удаление разрешено только для пустого клиента без единой финансовой операции. FK использует `ON DELETE RESTRICT`; каскадного уничтожения истории нет. Финансовые операции через UI не удаляются.

## 10. ADJUSTMENT

Единая семантика: `ADJUSTMENT.amount` — **signed NUMERIC**.

- `+25.00` увеличивает долг на 25;
- `-25.00` уменьшает долг на 25.

Любая корректировка, которая сделала бы итоговый баланс отрицательным, отклоняется серверной финансовой функцией. Текущий UI не показывает обычному пользователю кнопку ADJUSTMENT; это намеренно, чтобы ежедневный сценарий оставался простым.

## 11. CSV

**Настройки → Экспорт CSV** создаёт UTF-8 CSV с BOM для Excel. Поля с запятыми, `;`, кавычками и переносами строк экранируются. Файл предназначен для Apple Numbers и Microsoft Excel.

## 12. JSON backup

**Настройки → Резервная копия (JSON)** создаёт schema v2 с минимум:

- `schema_version`;
- `backup_id`;
- `exported_at`;
- `clients`;
- `transactions`.

Храните backup отдельно от телефона.

## 13. Restore — только безопасный REPLACE

Restore намеренно использует **REPLACE**, а не MERGE. Причина: для финансовых данных автоматический merge может незаметно задвоить одну и ту же историю.

Перед восстановлением приложение показывает количество клиентов и операций и требует явного подтверждения. Сервер валидирует структуру, типы операций, суммы, даты, связи client/transaction и запрет отрицательного баланса. Затем внутри одной транзакции заменяет данные аккаунта. При любой ошибке PostgreSQL делает rollback целиком.

Важно: REPLACE означает, что текущие `clients` и `transactions` аккаунта будут заменены backup. Поэтому сначала скачайте свежий backup текущего состояния. Повторный restore того же `backup_id` блокируется.

## 14. Аналитика

Проверьте после тестов:

- общий текущий долг;
- активные должники;
- выдано в долг за текущий месяц;
- получено оплат за текущий месяц;
- средний текущий долг;
- погашенные клиенты.

Source of truth — транзакции из PostgreSQL; frontend state после каждой успешной операции перечитывается из базы.

## 15. GitHub Pages

1. Создайте GitHub repository.
2. Загрузите все файлы проекта, включая папку `icons/`.
3. Убедитесь, что в `supabase.js` находится только URL + Publishable/anon key.
4. **Settings → Pages** → deploy from `main` / root.
5. Дождитесь HTTPS-ссылки GitHub Pages.

## 16. iPhone / PWA

1. Откройте HTTPS-ссылку в Safari.
2. Проверьте вход, список, карточку клиента, формы и scrolling.
3. Safari → **Поделиться → На экран «Домой»**.
4. Запустите приложение с Home Screen.
5. Проверьте safe areas сверху/снизу, клавиатуру, модальные экраны и отсутствие горизонтального scroll.
6. В DevTools/Application при возможности проверьте, что service worker активен и `dolgi-shell-v2` установлен.

В проекте реально присутствуют `icons/icon-192.png` и `icons/icon-512.png`. Отказ загрузки optional asset не валит установку service worker.

## 17. Финальный чек-лист перед реальными данными

- Новый account входит и сессия сохраняется.
- User A не видит User B.
- Initial migration: 44 / 24 920 сом.; повтор запрещён.
- Ошибка migration не оставляет partial data.
- +300, +50, -100 дают 250.
- PAYMENT > balance запрещён.
- Full payment переводит клиента в архив.
- Новый DEBT возвращает архивного клиента в активные.
- Double click/retry не создаёт дубль.
- Конкурентные PAYMENT не дают отрицательный баланс.
- Чужой `client_id` в RPC отклоняется.
- JSON restore атомарен; повтор backup_id запрещён.
- CSV открывается с кириллицей.
- PWA icons существуют; service worker устанавливается.
- Supabase API/Auth/RPC не кэшируются.
- На iPhone standalone нет horizontal overflow.

|---|---|
